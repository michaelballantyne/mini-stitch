# Stitch paper digest (POPL 2023, "Top-Down Synthesis for Library Learning")

Read-through of stitch.pdf to ground the mini-stitch design. This note records the
core algorithm and which pieces the paper's own evidence says are essential.

## Problem

Given a corpus of lambda-calculus programs (de Bruijn indices, s-expression syntax),
find the single abstraction (a function body over abstraction variables α, β, ...)
that maximizes a compression utility when the corpus is rewritten to use it. Iterate
to build a library: learn one abstraction, rewrite the corpus, repeat.

## Grammar (§3)

- Expressions: `e ::= (lam e) | (e e) | $i | prim`
- Abstraction bodies add abstraction variables: `A ::= ... | α`
- Partial abstractions add holes: `A?? ::= ... | ??`
- The search synthesizes the *body*; the abstraction is `λα0...αk. body`.

## Core algorithm: corpus-guided top-down search (§3.1, Appendix A)

Branch-and-bound over partial abstractions, starting from the single hole `??`:

1. Priority queue of partial abstractions keyed by utility upper bound (best-bound /
   A* order; paper says ordering only matters for anytime behavior, not total time).
2. Initialize best-so-far with the best arity-zero abstraction (best duplicated
   closed subtree — cheap complete enumeration).
3. Pop a partial abstraction, pick a hole (stitch picks the most recently introduced),
   enumerate all expansions: each primitive, `$i`, `(app ?? ??)`, `(lam ??)`, a fresh
   abstraction variable, or reuse of an existing abstraction variable.
4. Matching is incremental: match locations of an expansion are a subset of the
   parent's match locations (Lemma 2), and disjoint across syntactic expansions.
   No re-matching against the whole corpus; just inspect the subtree at each match
   location. Reusing an existing variable α restricts matches to locations where
   both uses see syntactically identical subtrees.
5. Prune an expansion if:
   - zero match locations;
   - upper bound ≤ best-so-far utility (upper-bound pruning);
   - strictly dominated (see below);
   - single match location without free vars (arity-zero abstraction is always
     at least as good there);
   - expansion is a free variable at the top level of the body (ill-formed), or
     exceeds max arity.
6. Complete abstraction (no holes left): compute exact utility, update best.

## Utility (§4.1)

Cost model: `cost_app = cost_lam = 1`, `cost_var = cost_ivar = cost_prim = 100`
(stitch defaults, used in all experiments).

Utility of abstraction A = `-cost(A) + Σ over rewrite locations of U_local(A, e)` where

```
U_local = cost_{α=0}(A)                        (structure removed at the site)
        - (cost_prim(t_A) + cost_app * arity)  (cost of applying the new primitive)
        + Σ_args (usages(α) - 1) * cost(arg)   (multiuse bonus: arg passed once,
                                                used many times)
```

Equivalent to the rewrite-based definition (Eq. 8) but computable without rewriting.

## Upper bound (§4.2)

`Ū(A??) = Σ over match locations of cost(subtree)` — i.e., pretend every match
site compresses to zero cost. Sound because match sets shrink monotonically.

## Strict dominance pruning (§4.3)

- **Redundant argument elimination**: if two variables α, β take identical arguments
  at every match location, the α-reusing abstraction dominates; discard.
- **Argument capture**: if a variable α takes the *same* argument at every match
  location, inlining that argument into the body dominates; discard. (Not applicable
  if the argument has free variables.) Slight non-optimality edge case (footnote 2),
  never observed to change results in the paper's experiments.

## Rewriting (§4.4)

Bottom-up DP over each program: at each node compute `util_R` (reject: sum of
children's `util*`), `util_A` (accept: `U_local` + args' `util*`), take max.
Then a top-down pass performs rewrites where accept > reject. Linear time, optimal
w.r.t. the utility; handles overlapping matches. De Bruijn shifts don't change
matchability or utility of a subtree, just bookkeeping.

## Variable/lambda subtleties (§3, Appendix B)

LambdaUnify with downshift `↓` and the special `&i` indices: when raising a subtree
out of a lambda, a variable bound exactly at that lambda becomes `&i` (a binding-rule
violation permitted only in hole bindings, never in abstraction-variable bindings).
Match locations whose α-bindings contain `&i` are discarded. In practice the
implementation tracks, per match location, whether candidate arguments contain
variables bound by lambdas *inside* the abstraction body — those can't be lifted
out as arguments.

## What matters, per the ablations (§6.4)

- **Argument capture**: essential — without it, most domains exhaust 50GB RAM.
- **Upper-bound pruning**: essential — 12x–208x more nodes explored without it.
- **Redundant argument elimination**: modest (1.0x–2.0x), domain-dependent.
- **No optimizations at all**: intractable everywhere.
- Structural hashing (hash-consing subtrees) is called out in Appendix A as an
  implementation-level necessity for equality checks and work sharing.

## Out of scope for a miniature (candidates)

- Parallelism (paper §3.1 notes it's easy but optional).
- Version spaces / deductive rewrite hybrid (§5, §6.5) — a prototype extension,
  not the core system.
- DreamCoder compatibility details: best-of-task metric (Eq. 18), single-task
  pruning, eta-long normal form.
- CLI breadth, dreamcoder JSON format conversion, non-default hole-choice orders.

## Testing resource

The real stitch builds cleanly in the submodule (`cargo build --release`) and runs
on `data/basic/*.json` (a corpus is just a JSON array of s-expression strings).
`data/expected_outputs/` has golden outputs with full config records. This enables
differential testing of mini-stitch against real stitch on identical corpora.
